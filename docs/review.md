# Qualified dependency review contract

Schema version 1 emits format/identity kind, parsing_status, dependency_kind_status, installed_path (null for resolution records), topology_status, root_attribution_status and execution_metadata_status alongside `status: complete|incomplete`, an explicit scope and byte hashes. `complete` refers to extraction within the selected scope. With explicit npm evidence it also requires every locked record to have qualified evidence. It never establishes runtime safety. JSON parse failures use an incomplete error envelope. Policy is separate: `advisory|allowed|blocked|incomplete` with `enforcement_requested` and unapproved bound fingerprints. [Execution evidence and approvals](execution-evidence.md) defines the stronger npm policy and input schemas.

npm instances use installation-path identities; pnpm uses full namespaced snapshot contexts, and Yarn uses canonical descriptor groups or Berry resolution locators. None are collapsed by package name. Nested/contextual versions remain distinct. Edges are directed and carry sorted kinds: dependencies, devDependencies, optionalDependencies, peerDependencies, workspaceLink, configDependencies and packageManagerDependencies. Unsourced Berry workspace edges use `workspaceDependencies` for their unknown merged kind. npm v1 transitive `requires` edges have an explicitly unknown dependency kind. Multiple kinds share one topology edge. npm optionalDependencies override same-name dependencies. Nearest installed node_modules instances resolve dependency targets; workspace links connect to lockfile workspace records. Missing required targets are issues; absent optional peers/optional dependencies are reported separately as optional omissions. Platform filtering is not inferred.

Without explicit npm evidence, positive install markers and supplied root lifecycle scripts appear in `execution_candidates`. Unreachable candidates have a null introducer path. With qualified evidence, verified lifecycle and implicit native-build facts determine candidacy. A positive marker disproved by a complete archive stays visible but is no longer a candidate.

Root `preinstall`, `install`, `postinstall`, `prepublish`, `preprepare`, `prepare`, and `postprepare` bodies are SHA-256 identified. Explicit npm evidence also inventories per-instance dependency and workspace lifecycle bodies. Binary entrypoints are identified separately because they do not automatically run during installation.

Paths include typed edges and use deterministic breadth-first traversal. pnpm paths seed every actual importer root, preferring project-dot on equal length, and expose `introducer_roots` and `path_scope`. They add no synthetic workspace or environment membership edges. Yarn source workspaces are also independent roots; no membership edges are invented. npm paths use the project root.

Marker-only reports remain advisory. Enforcement requires explicit evidence and bound approvals. Legacy `name@version` whitelist entries cannot authorize execution. Unknown pnpm or Yarn execution metadata always prevents an allowed enforcement outcome.

Reviews return complete base/head reports and package_changes keyed by the format-specific record identity (npm installation path, pnpm snapshot context or Yarn descriptor group). Same-version source/integrity changes are meaningful. Added/removed typed edges include edge-kind changes. `resolution_metadata` retains descriptor groups, peer constraints, aliases, pnpm checksums/directory fields and source context; `resolution_metadata_changed` identifies a metadata change even when graph edges are equal. Lock formatting-only changes affect byte hashes without creating package changes. Source manifest formatting changes invalidate byte-pinned evidence approvals. Unreachable records are included and identified; the lockfile is not asserted to reproduce a host's actual install selection.

Limits: npm lockfileVersion 1/2/3, pnpm 6.0/9.0, Yarn Classic v1 and Berry metadata 6/8/10 supported subsets; input JSON <=64 MiB with nesting <=128; strict grammar, duplicate-key rejection and finite numbers. Custom config supports three named keys with quoted strings/string arrays, comments and multiline arrays. Unsupported or invalid data fails visibly. The std-only SHA-256 identifies consumed bytes, not the publisher or artifact authenticity. Parser inputs are untrusted; arbitrary FFI pointers cannot be made safe by validation.

Math is diagnostic: a minimum-ratio-cut sweep over distinct coordinates of a bounded, diagonally preconditioned two-vector iteration, at most 5000 steps; residual convergence and iterations accompany every estimate. Residuals are recomputed from the returned estimate, and exhausting the work bound remains explicitly nonconverged. No exact lambda_2 or certified eigenpair claim is made. Candidate inventory and bound approval policy are independent of the cut. Disconnected graphs receive exact zero global connectivity but still retain every candidate in the report. See the [numerical evaluation](math-evaluation.md) and [cut-selection improvement](math-cut-improvement.md).

## Migration

Audits no longer run package managers or delete locks. Resolution snapshots do not claim installed instance placement. Cross-format comparisons return incomplete rather than compare incompatible keys. `--network`, the legacy daemon and unqualified CLI ecosystems return incomplete/usage errors. pnpm v6/v9 parsing preserves versions/peer and patch context, namespaces environment/project documents, retains importer/workspace links and validates root specifiers. Capabilities remain explicitly unknown. Yarn Classic v1 preserves exact grouped descriptors and source/integrity, with supplied-root attribution; explicit source manifests supply workspace/local-link context while installed peers are not inferred. Berry preserves exact locators, grouped descriptors, cache checksums and source-derived workspace dependency kinds. Unsupported Berry versions and Classic record structures are rejected. Legacy npm, pnpm and Yarn emit useful normalized graphs and diffs with overall incomplete/exit2 while transitive scripts are unknown. Cargo metadata parsing recognizes build scripts and proc macros but is an incomplete preview, without Cargo subprocesses. The retired semver/network API cannot guess resolution. Legacy coordinate whitelists must be replaced with explicit evidence-bound approvals. Existing threshold/mode values are validated but do not gate topology. Native result prefix is preserved; see the header for appended diagnostics and ownership.

## Explicit project inputs

`--project-inputs INDEX` supplies project-relative source bytes through a schema-v1 locator index; review accepts separate `--base-project-inputs` and `--head-project-inputs`. Each entry has exactly `path` and `file`. File locators are confined to the index directory, with no symlinks, absolute paths or parent traversal. Limits are 4 MiB per index, 10,000 entries, 1 MiB per file and 64 MiB aggregate source bytes. Duplicate logical paths and unknown schema fields are rejected. Only referenced manifests/configuration are parsed; unrelated malformed fixtures do not invalidate a project. A separately supplied root manifest must match bundled `package.json` bytes exactly.

`project_input_hashes` and `project_inputs_index_sha256` bind this caller-supplied context. No automatic filesystem discovery or source authenticity is implied. pnpm unconditional overrides are reconciled against supplied configuration, including catalog references; absent verification context remains an input-consistency issue. Workspace dependencies use exact locked targets or explicitly supplied source links. Missing source or required descriptors stays visible. Classic workspace selection supports numeric exact versions, validated exact prereleases, `*`, and numeric `^`/`~` ranges; other combinations remain explicitly unresolved instead of selecting a registry fallback. `*` excludes prereleases. Declared exact workspace paths must be supplied even when another workspace is present. Wildcard workspace inventory remains caller-supplied scope; an input bundle cannot prove that no matching Git directory was omitted. Project inputs cannot substitute for execution evidence or authorize approvals.

`parsing_status: complete` means the reader produced an inventory. `topology_status: complete` means required encoded/supplied graph references resolved; unknown execution, source consistency, root attribution, peer placement and v1 transitive kinds remain separately visible in statuses or issues. The overall report remains incomplete whenever any such issue remains. See the [200-project replay](parser-coverage.md) for measured coverage and real disagreements.
